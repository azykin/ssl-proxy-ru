# ssl-proxy-ru

HTTPS-шлюз для Google Apps Script и других клиентов, которым нельзя добавить свой удостоверяющий центр. По умолчанию он передаёт запросы портфельного отчёта в Т‑Инвестиции. Есть также режим для обычного HTTP API с одним заданным администратором HTTPS-адресом.

Google проверяет публичный сертификат вашего домена. Caddy принимает запрос и передаёт его шлюзу по внутренней сети Docker. Шлюз сам соединяется с API по TLS 1.2 или выше, проверяя цепочку и имя сервера. Для этого соединения к штатным корням Node.js добавлены три публичных сертификата НУЦ. Клиентского сертификата, закрытого ключа Минцифры и изменений в Google Таблицах на уровне TLS не требуется. [Параметры UrlFetchApp](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app) · [Требования Т‑Банка](https://developer.tbank.ru/invest/intro/developer/network) · [Происхождение и обновление сертификатов](certs/README.md)

## Запуск на своём сервере

Нужны Docker с Compose v2, домен с DNS-записью на сервер, доступные снаружи TCP 80/443 для Caddy и исходящий TCP 443 к банку. При наличии записи AAAA проверьте доступность и по IPv6.

```sh
git clone https://github.com/azykin/ssl-proxy-ru.git
cd ssl-proxy-ru
cp .env.example .env
install -d -m 700 secrets
(umask 077; openssl rand -hex 32 > secrets/proxy_key)
chmod 444 secrets/proxy_key
```

Впишите свой домен в `PROXY_DOMAIN` в файле `.env`. В каталоге `secrets` нужен режим `0700` на хосте. Compose монтирует в контейнер один файл, доступный непривилегированному процессу для чтения. Ключ генерируется один раз на установку. Для работающего шлюза используйте процедуру ротации ниже.

```sh
docker compose up -d --build
docker compose ps
# Замените имя на свой домен. Ожидается ответ ok.
curl --fail --show-error https://invest-proxy.example.com/healthz
```

`GET /healthz` проверяет процесс и входящий маршрут. Проверка соединения до самого банка описана ниже. На внешнем прокси или CDN выключите сохранение тел, заголовков авторизации и параметров URL. Любой оператор, завершающий TLS на этом пути, технически может прочитать токен банка и ответ.

**На платформе с управляемым HTTPS** разверните один [Dockerfile](Dockerfile), укажите `PROXY_KEY` как секрет из 64 hex-символов, выберите предоставленный платформой порт в `PORT` и направьте HTTPS-трафик на контейнер. Образ слушает `0.0.0.0:8080` по умолчанию. Вариант с файловым секретом использует `PROXY_KEY_FILE`. Укажите ровно один из двух. Публичный вход должен принимать финансовые запросы только по HTTPS. Для запуска напрямую из исходников нужны Node.js 24 и команда `node src/main.mjs`, адрес привязки по умолчанию в этом случае — `127.0.0.1`.

## Подключение Google Таблицы

1. Добавьте [TInvestProxy.gs](examples/TInvestProxy.gs) в проект Apps Script, которому принадлежит триггер обновления.
2. В **Настройки проекта → Свойства скрипта** укажите три значения из таблицы ниже. Сохраните банковский токен с правом «Только чтение», по возможности на нужный счёт. Редакторы этого проекта могут получить доступ к свойствам и менять код, исполняемый триггером. Если читателям таблицы нужны права редактирования, держите задачу и её секреты в отдельном проекте с ограниченным составом редакторов. [Права токенов Т‑Банка](https://developer.tbank.ru/invest/intro/intro/token)
3. Запустите `checkTInvestProxy()` в Apps Script. Он вызовет `UsersService/GetAccounts`, проверит структуру ответа и выведет в журнал только `GetAccounts HTTP 200`.
4. В существующей функции отправки запроса замените вызов `UrlFetchApp.fetch(...)` строкой `response = tInvestProxyFetch_(token, method, body);`. Она возвращает тот же тип `HTTPResponse`, поэтому обработка кодов, JSON и повторов для операций чтения может остаться в вызывающей функции. Прежняя константа базового URL банка больше не нужна. Функция чтения банковского токена может брать его из `PropertiesService.getScriptProperties().getProperty('TINVEST_TOKEN')`.

| Свойство | Значение |
| --- | --- |
| `TINVEST_PROXY_ORIGIN` | `https://invest-proxy.example.com` со своим доменом, без пути и завершающего слеша |
| `TINVEST_PROXY_KEY` | Значение локального `secrets/proxy_key` или секрета платформы `PROXY_KEY` |
| `TINVEST_TOKEN` | Отдельный банковский токен только для чтения |

У сервиса два независимых секрета. `X-Proxy-Key` проверяется шлюзом и удаляется перед отправкой. Стандартный `Authorization: Bearer …` доходит до банка. Шлюз не хранит токен между запросами. В Apps Script включена проверка сертификатов, переходы по редиректам отключены. Адрес прокси указывается непосредственно в запросе.

## Доступные маршруты

| Настройка | Разрешённые запросы |
| --- | --- |
| `PROXY_MODE=invest`, `RPC_MODE=portfolio` (по умолчанию) | Только POST к шести методам текущего отчёта. См. список ниже. |
| `EXTRA_RPC_METHODS=MarketDataService/GetCandles` | Добавляет конкретные RPC к портфельному режиму. Несколько имён разделяются запятой. |
| `RPC_MODE=all` | Любой метод REST API банка по каноническому пути. С торговым токеном разрешены в том числе торговые операции. |
| `UPSTREAM_ENV=sandbox` | Переключает банковский адрес на официальную песочницу. Нужен её токен. |
| `PROXY_MODE=upstream`, `UPSTREAM_ORIGIN=https://api.example.org` | Обычные GET, HEAD, POST, PUT, PATCH, DELETE и OPTIONS с путём и query исходного запроса на один настроенный сервер. `GET /healthz` зарезервирован. |

Портфельный профиль пропускает:

- `UsersService/GetAccounts`
- `OperationsService/GetPortfolio`
- `OperationsService/GetPositions`
- `OperationsService/GetOperationsByCursor`
- `InstrumentsService/GetInstrumentBy`
- `InstrumentsService/GetBondEvents`

Каждый путь начинается с `/rest/tinkoff.public.invest.api.contract.v1.`. Боевой адрес — `invest-public-api.tbank.ru`, адрес песочницы — `sandbox-invest-public-api.tbank.ru`. Для второго сервиса с другой политикой доступа поднимите отдельный экземпляр со своим ключом и одним фиксированным назначением.

В режиме `upstream` получатель задаётся при развёртывании. Например, запрос `GET https://proxy.example.org/v1/prices?id=42` поступит на `https://api.example.org/v1/prices?id=42`. Клиент передаёт ключ шлюза и, если требуется исходному API, обычный `Authorization`. Режим открывает владельцу ключа все пути настроенного API. Не направляйте его на внутреннюю административную панель или сервер общего назначения. Параметры банковского профиля в этом режиме оставьте по умолчанию.

## HTTP и защита данных

- Метод, путь, query и байты тела сохраняются. Передаются код и тело ответа, включая банковские ошибки, `Retry-After`, заголовки типа и кодировки содержимого. Сохраняется `Idempotency-Key`. Для обычного HTTP поддержаны диапазоны и условные запросы. Проходящие заголовки явно перечислены в [gateway.mjs](src/gateway.mjs).
- `Host` формируется из настроенного адреса. Служебные заголовки соединения, cookie, `Set-Cookie`, клиентские forwarded-заголовки и ключ шлюза наружу не передаются. CONNECT, WebSocket, gRPC streaming и работа в качестве системного forward proxy отключены.
- Ответы получают `Cache-Control: no-store`. Перенаправление upstream возвращает `502` без `Location`, чтобы клиент не повторил запрос с секретами на другом домене. Шлюз и поставляемый ingress не повторяют отправку запросов. При включении операций записи учитывайте, что таймаут после отправки не доказывает отмену операции на сервере.
- По умолчанию на экземпляр допускаются 16 одновременных запросов. Лимит частоты имеет запас 300 запросов и пополняется на 5 запросов в секунду. Тело запроса ограничено 1 МиБ, ответ 16 МиБ, чтение ответа upstream вместе с подключением — 25 секундами. Тела буферизуются в памяти. Для больших выгрузок пользуйтесь пагинацией.
- Штатная конфигурация не пишет заголовки, тела и URL в журналы запросов. Исключайте HTTP-трассировку и перехватывающий трафик APM на хостинге. Секреты, приватные ключи и локальный `.env` исключены из Git и контекста сборки. Публичные сертификаты добавлены только к исходящему HTTPS-клиенту.

## Если запрос не проходит

| Результат | Что проверить |
| --- | --- |
| Ошибка TLS в Apps Script при запросе к прокси | Публичный сертификат, доменное имя, DNS и доступность HTTPS-входа. |
| `401`, JSON `Invalid proxy key` | Сверьте ключ шлюза. Банковский `401` возвращается с исходным телом банка. |
| `400`, JSON `Bank bearer token required` | В банковском профиле нужен `Authorization: Bearer …`. |
| `403`, JSON `RPC method denied` | Метод не включён в профиль. Банковский `403` с другим телом может означать недостаточные права токена. |
| `429` | Ограничение шлюза или банка. Используйте `Retry-After`, если он задан. |
| `502` / `504` | Проверьте DNS, исходящий 443, цепочку, имя, время сервера и доступность банка из сети размещения. Шлюз возвращает `502` также при редиректе или превышении лимита ответа, `504` при собственном таймауте. |

[Проверка цепочки через OpenSSL](certs/README.md) не требует токена и не обращается к брокерскому счёту. Ту же проверку имени и цепочки из сети GitHub можно запустить кнопкой **Run workflow** в [Bank TLS connectivity](https://github.com/azykin/ssl-proxy-ru/actions/workflows/verify-bank-tls.yml). Она также выполняется при обновлении набора сертификатов и использует публичные корни Node.js вместе с НУЦ. При ротации ключа шлюза подготовьте новое значение в приватном каталоге, установите для файла режим `0444`, замените `secrets/proxy_key` и выполните `docker compose up -d --force-recreate gateway`. Запишите новый ключ в свойство Apps Script и повторите `checkTInvestProxy()`. При утечке банковского токена отзовите его в Т‑Банке отдельно.

## Аналоги и другие подходы

- **Такой же сбой в Google Sheets и Т‑Инвестициях.** Автор портфельного трекера описал собственную функцию Vercel с доверенными сертификатами. Для портфеля размещайте TLS-шлюз на инфраструктуре, которой доверяете. [GitHub, Relff/t-invest-portfolio-tracker](https://github.com/Relff/t-invest-portfolio-tracker/blob/main/PROXY-SETUP.md)
- **Пример Т‑Банка на Хабре.** В статье про инвестиционного ассистента сертификаты подключены внутри контейнера. Там описаны требования для банковского MCP и уровни доступа токенов. [Хабр, блог Т‑Банка](https://habr.com/ru/companies/tbank/articles/1086714/)
- **Похожая схема для публичных котировок.** Автор использовал собственный посредник для запросов из Google Sheets в MOEX ISS. У него другая причина проблемы и публичные данные. [Хабр, прокси для MOEX](https://habr.com/ru/articles/1001434/)
- **Сборщик без публичного входа.** Если перенос расписания допустим, задача на сервере может сама получить портфель официальным Python SDK с `SSL_TBANK_VERIFY=True` и записать результат в Sheets API. Для такого варианта потребуется настроить доступ на запись к таблице. [Режим SDK Т‑Банка](https://developer.tbank.ru/invest/intro/developer/network) · [Google Sheets API](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchUpdate)

## Тесты

В каталоге репозитория запустите `node --test` с Node.js 24 и OpenSSL 3. Тесты создают временные тестовые удостоверяющие центры и HTTPS-сервер. Проверяется передача запросов, отказ при недоверенной подписи или неверном имени, контроль доступа, лимиты и таймауты. Workflow [Gateway tests](.github/workflows/test.yml) также поднимает Docker Compose и проверяет вход через Caddy с локальным тестовым сертификатом.
